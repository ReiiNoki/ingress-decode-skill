## 1. Atbash

将字母表前后对折：

```
明文: abcdefghijklmnopqrstuvwxyz
密文: zyxwvutsrqponmlkjihgfedcba
```

- **提示词**：镜像、反转、对称、藏头不藏尾、A/Z、首尾
- **数字 Atbash**：有时也做 0↔9, 1↔8 对折
- **Hex Atbash**：十六进制字符也可以做类似翻转（0↔f, 1↔e, ...）

### 1.1 实战案例

```
密文: cbt33nzplgl878iw
→ Atbash 字母部分，数字保持
→ 明文: xyg33makoto878rd
```

**关键观察**：数字部分（33、878）直接保留不变，只有字母部分翻转。

### 1.2 排错

- 检查大小写是否混用（Atbash 大小写需要分别处理）
- 如果结果不通，试试**只翻转字母、保留数字**——这是最常见的模式
- 如果看起来应该翻转数字，用 `flip_digits=True`

## 2. ROT / Caesar 移位

- **ROT13**：字母移 13 位（自逆操作，同一函数加密=解密）
- **ROT5**：数字移 5 位（0↔5, 1↔6, ..., 4↔9）
- **ROT47**：可打印 ASCII（33-126）全范围移位
- **提示词**：shift、rotate、偏移、位移、转动

### 2.1 新手顺序

1. 先试 ROT13
2. 再试 ROT1 到 ROT25
3. 如果数字也参与，试 ROT5（或 ROT13+ROT5 组合）

### 2.2 实战案例（配合 Reverse + Typo）

```
密文: yd623qfztu63bhw
→ Reverse: whb36utzfq326dy
→ ROT-5（字母倒退5位）: rcw36poual326yt
→ 识别 typo: "poual" 应为 "portal"
→ 最终: rcw36portal326yt
```

### 2.3 排错

- ROT13 是自逆的，所以解不出来就说明不是 ROT13
- 如果字母解出来了但数字不对，试试单独对数字做 ROT5
- ROT 不改变字符类型（字母还是字母，数字还是数字）

## 3. Base64

### 3.1 特征

- 字符多为大小写字母、数字、`+`、`/`、`=`
- 长度接近 4 的倍数
- 结尾可能有 `=` 或 `==`

### 3.2 排错

- 是否漏字符
- 是否混入空格、换行、中文标点
- 是否需要先反转、Atbash 或替换符号
- 末尾是否缺少 `=` 填充（`quick_decode.py` 的 `decode_base64()` 会自动补全）

### 3.3 常见链路

```
原始密文 → Atbash → Base64 → 明文
原始密文 → Reverse → Base64 → 明文
原始密文 → Base64 → Base64（双层） → 明文
```

## 4. ASCII / Hex / Binary

### 4.1 常见形式

```
Hex:       48 65 6c 6c 6f        → "Hello"
Binary:    01001000 01101001     → "Hi"
Decimal:   72 105                → "Hi"
```

### 4.2 判断方法

- **Hex** 通常两个字符一组（0-9a-f）
- **Binary** 通常 8 位一组（0/1）
- **Decimal ASCII** 常见范围是 32 到 126
- 如果数字在 1 到 26 之间，优先试 **A1Z26**

### 4.3 A1Z26 详解

```
1=A, 2=B, 3=C, ..., 26=Z
```

示例：`1 26 6` → `a z f` → `azf`

### 4.4 排错

- Hex 解码失败检查是否有非 hex 字符混入
- Binary 检查位数是否 8 的倍数，不是的话考虑前面补 0
- Decimal 如果值 > 126，可能是其他编码（坐标、元素序号等）

## 5. Morse 电码

### 5.1 特征

- 出现 `.` 和 `-`
- 或只有**两种符号**，可以映射成长短、黑白、点横
- 题面暗示声音、节奏、电码、长短、敲击

### 5.2 注意

- 如果读不通，**交换点和横再试**
- 如果没有空格，先观察分组或图片排列
- 类 Morse 题经常需要先把符号替换成 `.` 和 `-`

### 5.3 高级变体：键盘行转 Morse

QWERTY 键盘三行映射摩斯：

| 键盘行 | 键位 | 映射 |
|--------|------|------|
| 顶行 | q w e r t y u i o p | 长划 `―` |
| 中行 | a s d f g h j k l | 短点 `·` |
| 底行 | z x c v b n m | 分隔符 `/` |

**可复现的最小示例**：

```
输入: qaz
q（顶行）→ -
a（中行）→ .
z（底行）→ 分隔符
得到: -. / → N
```

归档文章中的长案例无法由文章所述规则和当前工具复现，已在
`examples.md` 的案例 5 中标为“来源有误 / 未验证”，不可作为标准 Morse 示例。

### 5.4 排错

- 交换 `.` 和 `-` 再试一次
- 检查分隔符是否正确（字符间空格、单词间 `/`）
- 如果结果有连续相同字母，检查是否漏了分隔符

## 6. 盲文（Braille）

### 6.1 特征

- 六点式 Unicode 字符（⠁⠃⠉等）
- 信息数量能被 6 整除
- 提示词：盲、摸、点、六、3×2

### 6.2 标准做法

```
盲文字符 → 拉丁字母
```

### 6.3 非标准变体：按盲文点数运算

每个盲文字符由 6 个点组成（2 列 × 3 行）。部分谜题会提示对亮点数量进行运算，
但这不是通用盲文规则；必须由题面给出运算方式，并用实际算术验证。

### 6.4 实战案例

```
密文: ⠃⠧⠑⠎⠊⠑⠊⠎⠉⠊⠑⠝⠉⠑⠞⠺⠑⠊⠋⠕⠁⠎

① 盲文对照转拉丁字母:
b v e s i e i s c i e n c e t w e i f o a s
→ BVESIEISCIENCETWEIFOAS

② 识别 Ingress 标准 keyword: SCIENCE
→ 分段: BVE + SIEI + SCIENCE + TWEIFO + AS

③ 若按“每两个字符的亮点数相乘并取个位”计算:
S(3点) × I(2点) = 6
E(2点) × I(2点) = 4 → "64"

T(4点) × W(4点) = 16 → 个位 6
E(2点) × I(2点) = 4
F(3点) × O(3点) = 9 → "649"

④ 该结果与来源文章声称的 "68"、"284" 不一致，因此不能据此推出其最终 passcode。
```

> 勘误：来源文章的算术存在矛盾。这里只保留可验证的盲文转写与点数计算，
> 不把来源给出的最终字符串视作已验证答案。完整审计见 `examples.md` 案例 3。

### 6.5 排错方向

- 换读点顺序（从上到下 vs 从左到右）
- 旋转或镜像
- 黑白反转
- 重新分组

## 7. 键盘偏移（Typo / Keyboard Shift）

### 7.1 特征

- 解密结果接近单词，但字母像打偏了
- 提示词：keyboard、typo、手滑、左右、镜像
- 字符集中有大量相邻键

### 7.2 常试

- **QWERTY 左移一格**：如 `y→t`, `d→s`, `h→g`
- **QWERTY 右移一格**：如 `t→y`, `s→d`, `g→h`
- **键盘镜像**：左右翻转（如 `q→p`, `w→o`）
- **上下排错位**：如 `q→a`, `a→z`

### 7.3 实战案例

```
密文: yd623qfztu63bhw

① Reverse:
whb36utzfq326dy

② ROT-5（字母倒退5位）:
rcw36poual326yt

③ 识别 typo:
"poual" 不是单词 → 观察键位发现 "r"→"u"（手滑打偏）
且漏了 "t" → 应为 "portal"

④ 最终: rcw36portal326yt
```

### 7.4 排错

- 先做其他基础操作（Reverse、ROT），再做 keyboard shift
- typo 不一定是标准 shift——猩猩可能漏字符或打错键
- 如果中间结果接近单词但不对，尝试**手动补全**

## 8. 方阵 / 矩阵 / 重排（rect）

### 8.1 特征

- 长度是 16、24、25、36、64 等整齐数字
- 提示词：grid、matrix、square、rect、行列、宽度
- 字符本身不像加密，只像顺序被打乱

### 8.2 常试操作

- 按不同宽度换行（尝试所有因数）
- 横读、竖读、蛇形读
- 倒序、镜像、旋转 90°/180°
- 左下角开始从下往上逐行读取
- 对角线读法

### 8.3 实战案例：rect(4)

```
密文: 37koati52azmwoq3

① 16字符，排 4×4 矩阵:
3 7 k o
a t i 5
2 a z m
w o q 3

② 从左下角 w 开始，从下往上逐行向右读:
w o q 3 → woq3
2 a z m → 2azm
a t i 5 → ati5
3 7 k o → 37ko

③ 拼合: woq32azmati537ko
```

### 8.4 排错

- 尝试所有可能的列数（长度因数）
- 竖读和横读都试
- 蛇形读（之字形）：第一行从左到右，第二行从右到左
- 旋转 90° 后读

## 9. Playfair

Playfair 使用由 keyword 构造的 5×5 字母方阵，按两个字母一组变换。通常合并 `I/J`，
但题目可能指定其他合并方式。

### 9.1 识别信号

- 密文只含字母，清理后长度为偶数。
- 题面提示 pair、double、square、5×5、Playfair 或某个明显 keyword。
- 单字母频率分析效果较差，因为它按双字母替换。

### 9.2 解密步骤

1. 从题面确定 keyword；去重后填入 5×5 方阵，再补剩余字母。
2. 统一 `I/J`、大小写和非字母处理规则。
3. 将密文每两个字母分组。
4. 同行字母各向左移一格；同列字母各向上移一格；矩形四角则交换列。
5. 解密后谨慎处理为拆分重复字母或补齐长度而插入的 `X`；不能见到 `X` 就自动删除。

### 9.3 标准示例

```text
keyword: PLAYFAIR EXAMPLE
plaintext: HIDE THE GOLD IN THE TREE STUMP
ciphertext: BMODZBXDNABEKUDMUIXMMOUVIF
```

用同一方阵解密 ciphertext 应还原为规范化后的 plaintext。当前
`scripts/quick_decode.py` 未实现 Playfair；使用外部工具时必须记录方阵、`I/J` 规则和填充规则。

### 9.4 排错

- keyword 正确但结果不通：检查方阵是否去重、`I/J` 是否合并、加解密方向是否颠倒。
- 中间有异常 `X`：先判断它是原文字符还是填充字符，不要机械删除。
- 没有题面支持的 keyword 时，不要靠遍历词表强行挑可读结果。

## 10. Vigenère / AutoKey

两者都把字母映射到 `A=0 ... Z=25` 后做移位。Vigenère 重复 keyword；常见的
plaintext AutoKey 则先写 keyword，再用已恢复的明文继续扩展密钥。

### 10.1 识别信号

- 密文主要由字母组成，Caesar/ROT 无法整体解开。
- 题面提供 key、keyword、repeat、auto、self 等提示。
- Vigenère 的重复密钥可能产生周期；AutoKey 的周期通常不明显。

### 10.2 Vigenère 解密

```text
明文 P = (密文 C - 密钥 K) mod 26
```

标准示例：

```text
plaintext:  ATTACKATDAWN
key:        LEMONLEMONLE
ciphertext: LXFOPVEFRNHR
```

### 10.3 AutoKey 解密

以 keyword `QUEENLY` 为例，解密过程中把刚恢复的明文追加到密钥流：

```text
plaintext:  ATTACKATDAWN
key stream: QUEENLYATTAC
ciphertext: QNXEPVYTWTWP
```

AutoKey 存在不同变体，包括 ciphertext-autokey。必须先确认题目使用的变体，不能把一种
实现的失败直接当成 keyword 错误。`quick_decode.py` 提供 `vigenere()` 和明文扩展变体
`autokey_plaintext()`；其他 AutoKey 变体仍需单独实现并记录规则。

### 10.4 排错

- 确认使用 `A=0` 还是 `A=1`；经典实现通常使用 `A=0`。
- 确认加密方向、keyword 起始位置和非字母是否占用密钥位置。
- 结果前几位正确、后面失真时，优先检查 AutoKey 扩展方式或某个早期字符是否抄错。

## 11. Polybius / Bifid

Polybius 把字母表示为方阵坐标；Bifid 再把一段坐标的行、列数字分离重排，因此同时包含
替换和转置。常见方阵是 5×5 并合并 `I/J`。

### 11.1 标准 Polybius 方阵

```text
    1 2 3 4 5
1   A B C D E
2   F G H I K
3   L M N O P
4   Q R S T U
5   V W X Y Z
```

例如：

```text
24 33 22 42 15 43 43 → I N G R E S S
```

题目可能交换行列顺序、使用 keyword 方阵、从 0 编号或采用 6×6 字母数字方阵，必须保存原始分组。

### 11.2 Bifid 加密步骤

1. 用 Polybius 方阵把每个字母转成“行、列”坐标。
2. 按 period 分块；未给 period 时从题面、分组或长度因数寻找依据。
3. 加密时先连续写所有行数字，再写所有列数字，然后重新两两配对查表。

最小示例使用上面的标准方阵、period 4：

```text
F L E E → 21 31 15 15
行后接列: 2 3 1 1 1 1 5 5
重新配对: 23 11 11 55 → H A A Z
```

因此该设置下 `FLEE` 加密为 `HAAZ`；逆过程必须还原 `FLEE`。当前
`quick_decode.py` 未实现 Polybius/Bifid。

### 11.3 Bifid 解密步骤

对每个长度为 `n` 的 ciphertext 分块：

1. 将密文字母查表得到 `n` 组坐标，并按出现顺序展开为 `2n` 个数字。
2. 把数字流分成等长的前后两半；前半作为明文的行数字，后半作为列数字。
3. 将第 `i` 个行数字与第 `i` 个列数字重新配对，再查 Polybius 方阵得到明文字母。
4. 尾块按实际长度处理，不擅自补齐；每块都应使用相同方阵、period 和行列约定。

### 11.4 排错

- 结果完全不通：检查 keyword 方阵、`I/J` 合并和行列顺序。
- 局部正确：检查 period、分块边界和尾块处理方式。
- 数字只在 1–5：优先考虑 Polybius，但也要排除坐标、五进制和题面自定义索引。

## 12. Rail Fence

Rail Fence 把字符按锯齿路径写入若干行，再逐行读取。它只改变顺序，不改变字符本身。

### 12.1 识别信号

- 字符频率和字符集看起来正常，但顺序不通。
- 题面提示 rail、fence、zigzag、上下、轨道或波浪。
- rails 通常是小整数，可根据长度和题面有限尝试。

标准三栏示例：

```text
plaintext:  WEAREDISCOVEREDFLEEATONCE
ciphertext: WECRLTEERDSOEEFEAOCAIVDEN
rails:      3
```

项目工具已支持解密：

```python
decode_rail_fence("WECRLTEERDSOEEFEAOCAIVDEN", 3)
```

### 12.2 排错

- 尝试 rails 2–6 时保留所有输出及其依据，不只挑最像英文的一项。
- 区分 Rail Fence 与普通矩形列转置；后者按固定宽度排矩阵，不走锯齿路径。
- 标点和空格是否参与路径必须与题面一致。

## 13. 其他编码与领域线索

这些方法不是第一轮默认尝试。只有字符范围、分组、标题、图片或 Ingress lore 提供支持时再使用；
否则很容易从大量映射中挑出一个“碰巧可读”的结果。

| 方法 | 识别信号 | 处理方向 | 工具支持 |
| --- | --- | --- | --- |
| Leetspeak | 数字或符号替代字母 | 先做常见替换，再保留歧义项 | `leet_decode()` |
| URL 编码 | 大量 `%xx` | 按 UTF-8 百分号解码 | `decode_url_encoded()` |
| ROT47 | 字母、数字、标点混合 | 对 ASCII 33–126 旋转 47 | `rot47()` |
| 颜色编码 | 色块、颜色名、`#RRGGBB` | 保留顺序并检查 RGB、十六进制、互补色 | 需人工/图像工具 |
| 罗马数字 | `IVXLCDM` 或罗马主题 | 双向检查数字与字母串 | 需人工 |
| ASCII Art | 多行字符形成图形 | 保留等宽布局，尝试缩放、旋转和负空间 | 需人工 |
| 九宫格/T9 | 数字 2–9 重复分组或两位一组 | 按电话键盘映射，检查键号与按键次数顺序 | `decode_multitap_*()` |
| BCD | 0/1 且常按 4 位分组 | 每 4 位解释一个十进制数字 | 需人工 |
| 元素周期表 | 数字 1–118 或元素符号 | 原子序数与元素符号双向映射 | 需人工 |
| Ingress Glyph | 点线图形或 lore 提示 | 对照 Glyph 名称和语义，不凭形似硬猜 | 需领域资料 |

### 13.1 文本传输与字符替换

#### 13.1.1 URL 百分号编码

`%xx` 表示一个字节，而不是直接表示一个 Unicode 字符。先按字节解码，再根据上下文使用
UTF-8 或题目指定编码：

```text
%49%6E%67%72%65%73%73 → Ingress
```

`+` 在查询字符串中常表示空格，但在普通路径中可能就是加号。项目工具
`decode_url_encoded()` 可做基础解码；若结果含乱码，检查原文是否被重复编码、字符集是否错误，
或 `%` 是否只是普通分隔符。

#### 13.1.2 ROT47

ROT47 在可打印 ASCII 33–126 范围内旋转 47 位，会同时改变字母、数字和标点，并且自逆：

```text
Hello! → w6==@P → Hello!
```

题面只含字母时先考虑 Caesar/ROT13；字母、数字、标点混合且题面提示 rotate/47 时再试
`rot47()`。

#### 13.1.3 Leetspeak

Leetspeak 没有唯一映射，例如 `1` 可能是 `I`、`L` 或数字一，`5` 可能是 `S` 或数字五。
`leet_decode()` 只提供一组常见替换，因此必须保留歧义：

```text
1ngr355 → 可能是 ingress，也可能保留部分数字
```

只有标题、keyword 列表或 passcode 结构能解释选择时，才能确定具体字母。

### 13.2 九宫格 / Multi-tap / T9

标准电话键盘映射为：

```text
2 ABC   3 DEF
4 GHI   5 JKL   6 MNO
7 PQRS  8 TUV   9 WXYZ
```

常见模式有两种：

- **Multi-tap**：数字表示按键，重复次数表示该键上的第几个字母。
- **T9 predictive**：每个字母只写一次按键数字，同一数字串可能对应多个单词。

Multi-tap 示例：

```text
444 66 4 777 33 7777 7777 → I N G R E S S
```

空格、短横线或停顿通常用来分隔同一按键上的连续字母。没有分隔符时，不要擅自决定
`44` 是 `H`、两个 `G`，还是数字 44；列出候选并寻找题面支持。

### 13.3 BCD（二进码十进数）

最常见的 8421 BCD 用 4 bit 表示一个十进制数字：

```text
0000=0  0001=1  ...  1001=9
0100 0010 → 4 2 → 42
```

标准 BCD 中 `1010` 到 `1111` 不是有效十进制位。若四位组频繁落入这些范围，优先考虑
普通二进制、Hex、分组错位或其他编码。BCD 与二进制整数的区别是逐个十进制位编码：

```text
十进制 42 的 BCD: 0100 0010
十进制 42 的二进制: 0010 1010
```

遇到 packed BCD 时，一个字节包含两个十进制位；必须保留前导零和半字节边界。

### 13.4 罗马数字

标准符号是 `I V X L C D M`，常见减法组合为 `IV IX XL XC CD CM`。先按标准规则验证，
再考虑题目自定义变体：

```text
XIV → 14
MCMXCIX → 1999
```

纯字母串包含这些字符不等于罗马数字；需要罗马、帝国、世纪、序号或数值范围等线索。
反向把数字改写成罗马数字时，也要解释为什么答案需要字母而不是原数字。

### 13.5 元素周期表

这是低频领域映射，不是通用密码。只有数字集中在 1–118、题面出现化学/元素提示，或字符能自然
分成合法元素符号时才考虑：

```text
56 27 7 → Ba Co N → BACON
```

检查时注意：

- 元素符号首字母大写、第二个字母小写；分词边界会改变结果。
- 并非每个单字母都是元素符号，例如 `J`、`Q` 不存在，`G` 也不是现行元素符号。
- 原子序数、元素符号、英文名和化学性质是不同映射，必须由题面决定使用哪一种。
- 若多种切分都合法，结果只能标为“推测”，不能按期望 keyword 反向挑切分。

### 13.6 颜色、ASCII Art 与 Glyph

- **颜色**：记录精确 RGB/HEX 和顺序；只有题面支持时才尝试 ASCII 字节、互补色、通道拆分或颜色名首字母。具体提取流程见 `image-clues.md`。
- **ASCII Art**：保留等宽字体、空格和换行，分别检查前景与负空间，再尝试旋转或镜像。
- **Ingress Glyph**：记录节点、连线、方向和朝向，对照可靠 Glyph 表确认名称；相似轮廓、镜像和旋转可能代表不同概念。

Glyph 名称常提供 keyword 或操作提示，而不是直接给出完整 passcode。无法确认图形方向或缺少原图时，
保留多个候选并降低可信度。

这些方法常与 `passcode-format.md` 中的 keyword、图片和地图线索组合。图片承载的颜色、
元数据、二维码或隐藏文本按 `image-clues.md` 的检查流程处理。

## 14. Base32、Base85、UUencode 与 XOR

这些传输编码在归档中出现次数低于 Base64，但不能因此一律当成 Base64 失败。先根据字符表和
题面提示区分，再执行严格解码。

### 14.1 Base32

- 字符通常只含 `A-Z`、`2-7` 和末尾 `=`。
- 编码长度以 8 字符为一组；可能省略 padding。
- 归档 No.9、No.42、No.65、No.86、No.317 都出现 Base32 或相关提示。

```powershell
python -c "from scripts.quick_decode import decode_base32; print(decode_base32('JBSWY3DP'))"
```

不要因为字符串只含字母数字就同时宣称 Base32 和 Base64；比较两者字符范围、长度和严格解码结果。

### 14.2 Base85 / Ascii85

Base85 使用更大的可打印字符集，密度高于 Base64。归档 No.434 明确出现 Base85。
Python 的 RFC 1924 Base85 与 Adobe Ascii85 不是同一变体，失败时需要确认来源格式：

```python
decode_base85(text)                 # RFC 1924 Base85
decode_base85(text, adobe=True)     # Adobe Ascii85
```

### 14.3 UUencode

UUencode 常含大量标点，行首字符还编码该行字节数。归档 No.434 有单行案例。
使用 `decode_uu_line()` 时保留原始字符和行边界；不能先删除标点或自动换行。

### 14.4 XOR

XOR 必须同时有数据和 key。常见触发线索是：

- 一段 Hex 字节与一段已知明文长度相同。
- 页面中某句文字被密文替代，原句可作为 key 或 known plaintext。
- 题面明确提示 exclusive、either but not both、异或或 `^`。

`xor_hex_with_text()` 支持十六进制数据与循环文本 key。若 key 是一次性等长文本，循环不会产生差别。
没有题面支持时，不要遍历短 key 只挑可打印输出。

## 15. Gronsfeld

Gronsfeld 是数字密钥版 Vigenère：每个数字表示该位置的 Caesar 位移，密钥循环使用。
归档 No.132、No.198、No.366 中均出现，并且 key 往往来自同组另一个 code、字符计数或外部线索。

```text
ciphertext: IcBtTpWsHuFlbNC2
key:        1984
decrypt:    HtTpSgOoGlXhaEU2
```

```python
gronsfeld("IcBtTpWsHuFlbNC2", "1984")
```

检查事项：

- 明确数字是向前还是向后移。
- 非字母通常不消耗 key，但题目可能另有规定。
- key 是否循环、截断或与字母位置一一对应。
- 结果是 URL 时保留大小写；短链接通常区分大小写。

## 16. 游程、字符类别与多路二进制

### 16.1 交替游程编码

一串小数字可能表示连续 0、1 的长度，而不是直接转二进制。归档 No.205 的判断依据包括：

- 数值范围小。
- 所有游程长度之和是 8 的倍数。
- 从 0 或 1 开始交替展开后可按 8 位转 ASCII。

```python
decode_alternating_run_lengths(counts, start_bit="0")
decode_alternating_run_lengths(counts, start_bit="1")
```

两种起始 bit 都要检查，并记录为何选择其中一个。

### 16.2 字符类别映射

归档 No.422 展示了一个字符串按三种谓词同时解释成三个二进制串：元音/奇偶、
字母/数字符号、大小写/符号。遇到类似题面时先列清楚谓词，而不是直接写替换结果：

```text
规则 A：元音或奇数 -> 0，其余 -> 1
规则 B：字母 -> 0，数字或符号 -> 1
规则 C：小写或数字 -> 0，大写或符号 -> 1
```

选择谓词必须由字符分布、预期 code 数量或题面提示支持。对同一字符串尝试几十种任意分类并挑
可打印结果，属于过拟合。

### 16.3 一串多码

如果来源说明一个 post 通常有三个 code，而题面只有一个长串，检查：

- 大写、小写、数字、符号分别抽取。
- 奇偶位、每三位轮流抽取。
- 同一字符用不同谓词映射成多个 bitstream。
- 各层长度是否都能形成 16–24 字符左右的历史 passcode 候选。

最后仍要独立验证每一路，不能用“正好得到三个字符串”代替证据。

## 17. 算术序列与位置提取

归档中经常出现的不是标准 cipher，而是对数字序列做小规模、题面驱动的运算：

- 相邻差值、二阶差分。
- 平方、立方、连续开方。
- 数字之和、字符计数、重复次数、游程长度。
- 不同进制表示同一个数，再取“使用的进制”。
- 字母序与数值互换后再运算。

先写出原序列和变换后的完整序列，用脚本或手算复核；不要跳过不合预期的项。只有出现
“递增、差、power、cube、base、count”等线索，或数值呈明确结构时才尝试。

位置提取也很常见：

- 首字母、尾字母、藏头、藏尾。
- 每隔 N 位、Skip N、奇偶位。
- 第 N 个字母、月份/星期等固定词表中的指定位置。
- 从矩阵某角、某方向或某条对角线读取。

每次都记录索引从 0 还是 1 开始、是否包含空格和标点、越界如何处理。题目不给规则时，
大量枚举位置很容易制造伪明文。

## 18. 语言变换与 Keyword 补全

文章中许多 keyword 不是由标准密码直接输出，而来自语言和领域推理：

- 反义词或相对概念，例如 exit / ingress。
- 数字英文的前缀、后缀或缺失字母。
- 单词的前驱/后继、加减一个字母、单复数变化。
- 引文、人物、作品、地点和 Ingress lore 的外部搜索。
- 中间结果接近已知 keyword，但含 typo 或漏字。

这类步骤默认比确定性解码弱。报告时区分：

1. 原始算法实际输出。
2. 做了哪些补全或语言变换。
3. 题面提供了什么支持。
4. 是否存在同样合理的其他候选。

例如 `poual -> portal` 需要换字和补字，不能写成标准键盘移位的确定结果。只有来源承认 typo、
其他片段唯一指向 `portal`，或兑换/独立证据确认时，才能提高可信度。
