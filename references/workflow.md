## 1. 标准解题流程

### 1.1 抄干净

先把所有可疑信息单独记下来，**不要急着解**。

- 原始字符串，包括大小写、空格、换行、标点
- 标题、发布时间、链接、文件名、图片 alt 文本
- 图片里的文字、颜色、形状、排列、数量
- 是否有明显分组，例如 2、3、5、6、8 个一组
- 是否存在异常：错别字、大小写突变、奇怪符号、重复字母、缺失字符

> 很多题的突破口不是算法，而是"多看了一眼"。

### 1.2 判断字符类型

看字符集、长度和分组方式缩小范围，再按需查 `cipher-patterns.md` 的算法特征。

### 1.3 低成本操作（第一轮）

这些操作简单、命中率高，适合作为第一轮：

1. **反转字符串**（Reverse）
2. **Atbash 字母翻转**
3. **ROT13**，必要时试 ROT1 到 ROT25
4. **数字 ROT5**（0↔5, 1↔6, ...）
5. **A1Z26**（1=A, 2=B ... 26=Z）
6. **Base64 decode**
7. **Hex / Binary / Decimal ASCII**
8. **Morse**
9. **键盘左移、右移、镜像**

> 如果某一步得到的是"更像线索"的东西，不要急着停。Ingress 题经常是多层结构，第一层结果可能只是下一步提示。

## 2. 多层解密链路

### 2.1 典型链路

```
原始密文 → Atbash → Base64 → Morse → keyword → 拼 passcode
原始密文 → Reverse → ROT5 → 识别 typo → keyword → 拼 passcode
原始密文 → 盲文转字母 → 识别 keyword → 验证题面指定的后续规则
原始密文 → 排矩阵 → 竖读 → 拼接 → 拼 passcode
```

### 2.2 每层记录

- 这一层用了什么方法
- 为什么想到这个方法
- 输出结果是什么
- 输出结果更像：**答案**、**线索提示**、**下一层密文**

### 2.3 一层解完不是 Passcode 时的可能性

- 是下一层密文
- 是操作提示（如"try ROT13"、"use base64"）
- 是 keyword
- 是 URL 或搜索关键词
- 是地点、人物、物品名

## 3. 新手排错清单

卡住时按这个顺序检查：

1. 原文有没有抄错
2. 大小写有没有保留
3. 空格和换行有没有被误删
4. 中文标点和英文标点有没有混用
5. 是否需要反转字符串
6. 是否需要交换两种符号（如 Morse 的点与横）
7. 是否需要换分组方式
8. 是否漏看标题、文件名、链接、图片
9. 是否把中间提示误当最终答案
10. keyword 是否只是脑补，缺少题面支持
11. 是否需要在 Atbash 后接 Base64，或 Base64 后接 Morse
12. 是否忽略了"猩猩手滑"（typo/拼写错误）的可能性
13. **是否试过用 `scripts/quick_decode.py` 的 `scan_all()` 一键扫描**

## 4. 结论可信度

可信度评价的是“当前证据能否推出当前结论”，不是字符串看起来有多像 passcode。

| 等级 | 使用条件 |
| --- | --- |
| **已验证** | 每一步规则明确且可重复执行；计算或标准码表一致；最终各片段均有来源；没有影响结论的未解释线索 |
| **高可信** | 主要链路可复现且题面支持充分，但缺少兑换、原始文件或某项外部验证；剩余不确定性不改变核心结果 |
| **推测** | 至少一个关键步骤依赖 keyword 猜测、手动补字、模糊图形、多个同样合理的参数或其他未证实假设 |
| **未验证** | 无法按所述规则复现，或结果与算术、标准码表、工具输出、原始题面明显矛盾 |

### 4.1 评级规则

- Passcode 已过期或无法兑换，不妨碍通过完整可复现链路达到“已验证”。
- “符合格式”“出现 Ingress 单词”或“来源文章这样写”不能单独提高可信度。
- 多层题按最弱关键步骤评级；前几层正确、最后靠猜，整体仍是“推测”。
- 缺少原图、元数据或上下文时，写明缺失证据；如果缺失项可能改变答案，不得标为“已验证”。
- 发现算术或码表矛盾时标为“未验证”，保留来源声称与可复现结果，不替来源强行圆答案。

报告结论时同时给出：等级、支持证据、关键假设、未解释线索和下一步验证方法。
